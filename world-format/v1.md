# World Format v1 Specification

## 1. Purpose

World Format v1 defines the persistent binary representation of a world used by the `Conscious` simulation.

The format is **versioned**, **binary**, and uses **big-endian byte order** for all numeric values.

The format describes the **semantic state of the world**, rather than the internal C representation used at runtime.

The v1 format contains:

* world dimensions;
* exactly one mandatory terrain layer;
* a dense heightmap representing the terrain elevation.

Future versions may introduce additional layer types, storage methods, or other kinds of world state.

---

# 2. General format

Every world file starts with an 8-byte header:

| Offset | Size | Type        | Meaning             |
| -----: | ---: | ----------- | ------------------- |
|    `0` |    4 | byte string | World magic: `CWLD` |
|    `4` |    4 | `uint32`    | Format version      |

For v1:

```text
43 57 4C 44 00 00 00 01
```

where:

* `43 57 4C 44` = `CWLD`
* `00 00 00 01` = version `1`

All multi-byte numeric values use **big-endian** byte order.

---

# 3. World metadata

Immediately after the common header, v1 stores the dimensions of the world.

| Offset | Size | Type     | Meaning     |
| -----: | ---: | -------- | ----------- |
|    `8` |    4 | `uint32` | World width |
|   `12` |    4 | `uint32` | World depth |

Both values are expressed in **millimetres**.

There is no unit field in the file.

The unit is defined by the format:

> **1 world unit = 1 millimetre.**

Therefore:

```text
width  = 10000
depth  = 10000
```

represents a world measuring:

```text
10 m × 10 m
```

The dimensions are part of the world itself. They are not properties of an individual layer.

---

# 4. Layer structure

After the world metadata, v1 contains exactly one mandatory layer:

```text
TYPE_HEIGHTMAP
```

The beginning of a layer is identified by a fixed 4-byte marker:

```text
_LYR
```

Binary representation:

```text
5F 4C 59 52
```

There is no additional generic layer header.

The layer metadata follows the `_LYR` marker directly.

---

# 5. v1 layer layout

The complete v1 layer is:

| Field          |     Size | Type / representation  |
| -------------- | -------: | ---------------------- |
| Layer marker   |        4 | `"_LYR"`               |
| Layer type     |       16 | Fixed-size byte string |
| Layer name     |       16 | Fixed-size byte string |
| Evolution      |        4 | Fixed-size byte string |
| Storage type   |        4 | Fixed-size byte string |
| Cell size      |        4 | `uint32`               |
| Minimum height |        4 | `int32`                |
| Height values  | variable | `uint32` array         |

Therefore, the layer prefix before the height data occupies:

```text
4 + 16 + 16 + 4 + 4 + 4 + 4 = 52 bytes
```

---

# 6. Layer marker

Every layer begins with:

```text
_LYR
```

This is a fixed four-byte marker:

```text
5F 4C 59 52
```

The marker identifies the beginning of a layer.

A file that does not contain the expected marker at this point is invalid.

---

# 7. Layer type

The layer type is stored in a fixed 16-byte field.

The v1 terrain layer has the type:

```text
TYPE_HEIGHTMAP
```

The string occupies 14 bytes and is followed by two zero-padding bytes:

```text
54 59 50 45 5F 48 45 49 47 48 54 4D 41 50 00 00
```

The layer type identifies the **semantic kind of layer**.

It is distinct from the layer name.

For example:

```text
TYPE_HEIGHTMAP
```

means that the layer represents a heightmap, whereas:

```text
LYR_HEIGHTMAP
```

is the identifier/name of this particular layer.

In v1, `TYPE_HEIGHTMAP` is the only defined layer type.

---

# 8. Layer name

The layer name is stored in a fixed 16-byte field.

The v1 heightmap has the name:

```text
LYR_HEIGHTMAP
```

The field is zero-padded on the right to exactly 16 bytes.

The layer name identifies the particular layer.

The distinction is:

```text
Layer type:
    TYPE_HEIGHTMAP

Layer name:
    LYR_HEIGHTMAP
```

The type describes **what the layer is**.

The name identifies **which layer it is**.

---

# 9. Evolution

The evolution field is four bytes:

```text
EV_N
```

Binary representation:

```text
45 56 5F 4E
```

`EV_N` means that the layer has no additional evolution/variant mechanism defined by v1.

The field exists so that future versions can define different layer evolution mechanisms without changing the basic organization of the layer.

---

# 10. Storage type

The storage type is four bytes:

```text
ST_D
```

Binary representation:

```text
53 54 5F 44
```

`ST_D` means **dense storage**.

The heightmap therefore contains one stored elevation value for every terrain cell.

v1 defines no sparse heightmap representation.

---

# 11. Cell size

The cell size is a `uint32` stored in big-endian byte order.

It is expressed in millimetres.

For example:

```text
cell_size = 1000
```

means:

```text
1 metre × 1 metre
```

The cell size belongs to the **heightmap layer**, not to the world.

This distinction is intentional.

For example, the same world may have:

```text
World:
    10000 mm × 10000 mm

Terrain:
    cell size = 1000 mm
```

giving:

```text
10 × 10 terrain cells
```

while another layer in a future format could use a different spatial resolution.

---

# 12. Minimum height

The minimum height is a signed 32-bit integer:

```c
int32_t
```

stored in big-endian byte order.

It is expressed in millimetres.

The value stored in the heightmap as elevation code `0` corresponds to `min_height`.

For example:

```text
min_height = 1000
```

means that a heightmap value of:

```text
0
```

represents an elevation of:

```text
1000 mm
```

or:

```text
1 m
```

The field is signed because terrain elevation may be below the chosen reference level.

For example:

```text
min_height = -5000
```

represents:

```text
-5 m
```

---

# 13. Heightmap dimensions

The number of cells along each dimension is determined from the world dimensions and the layer cell size.

```text
cell_width = width / cell_size
cell_depth = depth / cell_size
```

For v1, both divisions must be exact:

```text
width % cell_size == 0
depth % cell_size == 0
```

Otherwise the file is invalid.

The total number of height values is:

```text
cell_count = cell_width × cell_depth
```

Every value occupies four bytes.

Therefore the heightmap data size is:

```text
cell_count × 4
```

bytes.

---

# 14. Height values

Each height value is an unsigned 32-bit integer:

```c
uint32_t
```

stored in big-endian byte order.

The value represents an elevation offset from `min_height`.

Conceptually:

```text
elevation = min_height + height_value
```

where both quantities are expressed in millimetres.

For example, if:

```text
min_height = 1000
height_value = 7
```

then:

```text
elevation = 1007 mm
```

or:

```text
1.007 m
```

The use of an unsigned value allows a large positive range above `min_height`.

---

# 15. Heightmap ordering

The heightmap is stored as a sequence of rows.

For each row, values are written from left to right.

The rows are then written in order from the first row to the last row.

Conceptually:

```text
row 0: cell(0,0) cell(1,0) ... cell(W-1,0)
row 1: cell(0,1) cell(1,1) ... cell(W-1,1)
...
row D: ...
```

where:

```text
W = width / cell_size
D = depth / cell_size
```

The corresponding linear index is:

```text
index = row × cell_width + column
```

Thus:

```text
values[0]
```

is the first cell of the first row, and:

```text
values[cell_width - 1]
```

is the last cell of the first row.

---

# 16. Complete v1 binary layout

The complete file is:

```text
+--------------------------+
| CWLD                     | 4 bytes
+--------------------------+
| Version = 1              | 4 bytes
+--------------------------+
| Width                     | 4 bytes
+--------------------------+
| Depth                     | 4 bytes
+--------------------------+
| _LYR                      | 4 bytes
+--------------------------+
| TYPE_HEIGHTMAP            | 16 bytes
+--------------------------+
| LYR_HEIGHTMAP             | 16 bytes
+--------------------------+
| EV_N                      | 4 bytes
+--------------------------+
| ST_D                      | 4 bytes
+--------------------------+
| Cell size                 | 4 bytes
+--------------------------+
| Minimum height            | 4 bytes
+--------------------------+
| Height value 0            | 4 bytes
+--------------------------+
| Height value 1            | 4 bytes
+--------------------------+
| ...                       |
+--------------------------+
| Height value N-1          | 4 bytes
+--------------------------+
```

The first height value therefore starts at offset:

```text
16 + 52 = 68
```

# 18. Validation requirements

A v1 loader must reject a file if any of the following conditions occurs.

## 18.1 Invalid world magic

The first four bytes must be:

```text
CWLD
```

Otherwise:

```text
WORLD_ERROR_INVALID_MAGIC
```

is returned.

## 18.2 Unsupported version

The four-byte version field must contain:

```text
1
```

for v1.

An unsupported version produces:

```text
WORLD_ERROR_UNSUPPORTED_VERSION
```

## 18.3 Truncated data

Any field that cannot be completely read produces:

```text
WORLD_ERROR_TRUNCATED
```

This applies to:

* header;
* world dimensions;
* layer marker;
* layer metadata;
* cell size;
* minimum height;
* every height value.

## 18.4 Invalid dimensions

The following are invalid:

```text
width == 0
depth == 0
```

## 18.5 Invalid cell size

The following is invalid:

```text
cell_size == 0
```

## 18.6 Non-integral cell dimensions

Both dimensions must be divisible by the cell size:

```text
width % cell_size == 0
depth % cell_size == 0
```

Otherwise the format is invalid.

## 18.7 Invalid layer marker

The expected marker is:

```text
_LYR
```

Any other value is invalid.

## 18.8 Invalid layer type

v1 defines exactly one layer type:

```text
TYPE_HEIGHTMAP
```

Any other layer type is invalid in v1.

## 18.9 Invalid layer metadata

The fixed-size string fields must contain their defined values and use zero padding where applicable.

For example, the 16-byte layer type field must contain:

```text
TYPE_HEIGHTMAP
```

followed only by zero-padding bytes.

Likewise, the layer name field must contain:

```text
LYR_HEIGHTMAP
```

followed only by zero-padding bytes.

## 18.10 Missing heightmap

The heightmap is mandatory in v1.

A v1 world without the heightmap layer is invalid.

## 18.11 Duplicate heightmap

v1 defines exactly one heightmap layer.

More than one:

```text
TYPE_HEIGHTMAP
```

layer is invalid.

# 19. Runtime representation

The binary representation does not have to match the C runtime representation.

The current runtime representation is conceptually:

```c
typedef struct {
    uint32_t cell_size;
    int32_t min_height;
    uint32_t *values;
} world_heightmap_t;

typedef struct {
    uint32_t format_version;
    uint32_t width;
    uint32_t depth;
    world_heightmap_t heightmap;
} world_state_t;
```

The `values` member is a dynamically allocated array in memory.

The binary file does not contain a pointer. It contains the actual height values.

Similarly, runtime-only data structures may exist in future versions without being persisted in the world file.

---

# 20. Serialization policy

The world format uses asymmetric compatibility:

### Reading

The loader is intended to support older world formats.

For example:

```text
v0 file → current runtime
v1 file → current runtime
```

As new formats are introduced, older formats can continue to be accepted where compatibility is maintained.

### Writing

The serializer writes only the **current/latest supported format**.

The current serializer therefore writes:

```text
World Format v1
```

It does not select an older writer according to `world->format_version`.

Consequently, the runtime may load an older world and then serialize it using the current v1 representation.

---

# 21. v1 implementation scope

World Format v1 is deliberately concrete.

It defines:

* one world dimension system;
* one layer marker;
* one layer type;
* one layer name;
* one evolution mode;
* one storage mode;
* one dense heightmap.

The current implementation therefore represents the heightmap directly as:

```c
world->heightmap
```

rather than introducing a generic runtime array of arbitrary layers.

The v1 serializer writes exactly one mandatory heightmap layer.

Generic layer collections and additional layer types are deferred to a future format revision when there is an actual requirement for them.

---

# 22. Semantic limitations

The v1 heightmap represents terrain as a single elevation value for each horizontal cell.

Consequently, it cannot represent multiple terrain surfaces at the same horizontal position.

For example, it cannot directly represent:

```text
surface
   |
cave
   |
surface
```

because a single `(x, y)` position has only one stored height.

This is a limitation of the **v1 heightmap representation**, not necessarily a limitation of the broader `TERRAIN` concept.

A future format may introduce another terrain representation capable of representing multiple surfaces or volumetric geometry.

For the standard 10 m × 10 m test world, the beginning of the file is:

```text
Offset  0:
    CWLD

Offset  4:
    00 00 00 01

Offset  8:
    00 00 27 10
    10000 mm

Offset 12:
    00 00 27 10
    10000 mm

Offset 16:
    _LYR

Offset 20:
    TYPE_HEIGHTMAP + zero padding

Offset 36:
    LYR_HEIGHTMAP + zero padding

Offset 52:
    EV_N

Offset 56:
    ST_D

Offset 60:
    00 00 03 E8
    1000 mm

Offset 64:
    00 00 03 E8
    1000 mm

Offset 68:
    first height value = 1000

Offset 72:
    second height value = 1001

...

Offset 464:
    last height value = 1009
```

The last height value is at offset `464` and occupies bytes `464–467`.

Therefore:

```text
file size = 468 bytes
```

# 24. Summary

The v1 world file has this fundamental structure:

```text
WORLD
├── magic: CWLD
├── version: 1
├── width: uint32, millimetres
├── depth: uint32, millimetres
│
└── LAYER
    ├── marker: _LYR
    ├── type: TYPE_HEIGHTMAP
    ├── name: LYR_HEIGHTMAP
    ├── evolution: EV_N
    ├── storage: ST_D
    ├── cell_size: uint32, millimetres
    ├── min_height: int32, millimetres
    └── values: uint32[cell_width × cell_depth]
```

All numeric values are **big-endian**.

The world dimensions belong to the world.

The cell size belongs to the heightmap layer.

The heightmap is dense, mandatory, and unique in v1.

The format is intentionally simple and explicit; extensibility beyond the currently defined heightmap is deferred to future versions rather than being encoded through abstractions that v1 does not yet need.
